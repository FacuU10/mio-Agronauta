# Exploration: ibera-alerta-pna-ingest-safe-fix

### Current State

Production smoke now proves the web/API route is reachable: both `https://agronauta.onrender.com/api/hydrology/municipalities` and `https://www.agronauta.com.ar/api/hydrology/municipalities` return `200 OK`, but they still serve old/offline fixture data. The remaining production failure is source-specific: `POST /api/hydrology/ingest` with `source=PNA` returns `202` but the structured ingest result is `failed` with `Hydrology ingestion failed for PNA: timeout after 12000ms`.

The current Express ingest runner seeds municipalities, then processes requested sources sequentially. For each source it wraps `client.fetchTelemetry()` in `fetchWithDeadline(clients[source], 12_000)`. `PnaHttpClient` itself also has an internal `AbortController` timeout, defaulting to `15_000ms`, and already sends a browser-like `User-Agent`, `Accept`, and `Accept-Language` headers. Because the runner-level deadline is shorter than the client-level abort, the exact production error is generated by the outer runner timeout before the PNA fetch can abort and classify its own network failure. That means the HTTP request may remain in flight until the inner 15s abort even though the ingest result has already been marked failed.

PNA URL configuration already exists through `HYDROLOGY_PNA_URL`, defaulting to `https://www.prefecturanaval.gob.ar/alturas`, but the default page/parser contract is fragile: `PnaAdapter` only extracts rows with `<tr data-station="...">`, and the default public page may be slow, blocked from Render, or not machine-readable in the expected shape. Production-safe behavior is already partly present: production does not write offline fixtures on failure; it persists a failed run and keeps existing municipality data available.

### Affected Areas

- `packages/hydrology-engine/src/clients/http-clients.ts` — PNA HTTP client, provider URL env override, default headers, client timeout, and network/parse error classification.
- `packages/hydrology-engine/src/adapters/pna-adapter.ts` — PNA parser expects specific `data-station` HTML rows and hardcodes provenance URL to the default PNA page.
- `apps/api/src/presentation/routes/hydrology-government.ts` — ingest runner hardcodes a 12s outer source deadline, persists per-source failures, and returns the public ingest contract.
- `packages/zod-schemas/src/agronautas.ts` — ingest response schema currently allows `errorMessage`/`provenanceUrl` but no structured per-source diagnostic object.
- `apps/api/src/infrastructure/jobs/hydrology-ingestion-scheduler.ts` — scheduled PNA cadence is hourly and unchanged-data retry is one delayed retry at +15m; any implementation must avoid adding retry storms.
- `apps/web/src/app/api/hydrology/[...path]/route.ts` — production web BFF forwards POST bodies and preserves upstream status/body for `/api/hydrology/ingest`.
- `openspec/specs/ibera-alerta/spec.md` — existing production-safe ingest requirements already require independent per-source results, no production fixture writes, configurable provider URLs, and graceful degraded behavior.

### Approaches

1. **Unify source timeout and diagnostics without retries** — Make PNA timeout budget explicit and source-specific, ensure the active `fetch` is aborted by the client within the runner budget, and return/persist structured diagnostics such as `source=PNA`, `reason=timeout`, `timeoutMs`, configured provider host/path, and `attempts=1`.
   - Pros: Directly addresses the observed 12s timeout; bounded one-request behavior; improves production debugging without increasing provider load.
   - Cons: Does not solve provider-side slowness if the configured PNA URL is not machine-readable or unreachable from Render.
   - Effort: Medium

2. **Provider URL override plus verified machine-readable endpoint** — Keep the client bounded but require production `HYDROLOGY_PNA_URL` to point at a verified PNA-compatible endpoint/feed if the default page is unsuitable.
   - Pros: Best long-term robustness if the official default page is slow or parser-incompatible; already aligned with existing env override design.
   - Cons: Needs ops/provider validation; cannot be proven from repo code alone.
   - Effort: Low/Medium

3. **Circuit-breaker/cooldown for manual and scheduled PNA ingest** — Add a short in-process source cooldown after PNA timeout/failure so repeated operator clicks or scheduler overlap return `skipped`/degraded instead of contacting PNA again immediately.
   - Pros: Strong anti-DDoS guard and graceful degradation; protects official source during outages.
   - Cons: In-memory state resets per deploy/instance unless backed by DB; must not hide legitimate single smoke attempts.
   - Effort: Medium

### Recommendation

Proceed with a combined safe fix: keep PNA ingest single-attempt, configure a source-specific PNA client timeout lower than or equal to the runner budget, remove/avoid the outer timeout masking the client abort, add structured source diagnostics to the ingest result, and introduce a conservative PNA cooldown/circuit-breaker only for repeated failures. Do not add automatic retries beyond the existing scheduler policy; if a real smoke is needed, run exactly one `POST /api/hydrology/ingest` with `source=PNA` and a clear reason after deploy.

### Anti-DDoS Verification Plan

- Unit-test that one PNA ingest calls the configured fetch exactly once and never loops/retries on timeout.
- Unit-test that timeout produces a failed PNA result with `attempts=1`, timeout classification, provider provenance, and zero fixture records written in production mode.
- Unit-test cooldown/circuit behavior, if implemented: the second immediate PNA request after a timeout returns `skipped` or equivalent degraded diagnostic without calling fetch again.
- Unit-test that non-PNA sources are not blocked by a PNA failure and top-level status remains `partial` when another source succeeds.
- Production smoke must be single-attempt only: one GET municipalities check, then one POST ingest with `source=PNA` and `reason=production-pna-safe-smoke`; no loops, no aggressive polling, no repeated retries after timeout.

### Risks

- The official PNA host may be slow, block Render egress, or expose HTML that no longer matches `PnaAdapter`; code can classify this safely but may still need a verified official provider URL.
- Adding diagnostics requires schema/client compatibility work because the current Zod response strips unsupported fields.
- In-memory cooldown is helpful but not distributed; a DB-backed ingest-run/cooldown check is safer if multiple API instances can handle ingest.
- Existing scheduled PNA retry for unchanged heights is bounded to one delayed retry, but manual ingest must not bypass future cooldown protections.

### Ready for Proposal

Yes. Proposal should scope a bounded PNA-only ingest robustness fix: explicit source timeout, no retry storm, source diagnostics, optional provider URL validation, graceful degradation/cooldown, and single-attempt production smoke evidence.
