### Existing Iberá-Alerta contracts and workflows

- `GET /api/hydrology/municipalities` returns a province overview, source freshness, province alerts, municipality records, latest telemetry, official alert projections, gauge mappings, and coverage gaps.
- `GET /api/hydrology/municipalities/:id/dashboard` returns telemetry cards, INA forecasts limited to 30 days, official alert telemetry, provenance, coverage gaps, a threshold/source-mapping explanation, and a bounded timeline.
- `POST /api/hydrology/ingest` is authenticated and asynchronously admits a source-scoped or all-source run. `GET /api/hydrology/ingest/:runId` observes a bounded status path. `GET /api/hydrology/ingest/runs` exposes authenticated durable run history.
- Municipality Copilot context is deliberately restricted to supported zones and official telemetry. The route explicitly rejects hydraulic routing, propagation/lag, caudal/represa discharge, and evacuation-authority requests.
- The shared contracts already have versioned schemas for municipality overview/dashboard, ingest results and diagnostics, durable run history, municipality explanations, municipality timelines, evidence state, and Copilot citations. They are additive seams rather than evidence that a larger institutional model exists.

### Municipality, zone, and geometry evidence

- `PNA_FLOOD_RISK_PORTS` currently defines 17 Corrientes localities/ports, threshold values, river labels, station IDs, and source mappings. INA has three explicitly configured series (`6764`, `33988`, `38469`). SMN and INMET mappings are finite seeded associations.
- `seedGovernmentMunicipalitiesIfEmpty()` writes municipality rows, mappings, and station rows idempotently. The municipality table stores PostGIS `MultiPolygon` boundaries and has a GIST index.
- The seed boundary is generated by `squareBoundary()` around a monitored port. It is not an official administrative boundary. PostGIS storage/indexing therefore proves persistence capability, not territorial correctness.
- Neither the municipality contract nor the repository view includes geometry coordinates, geometry source, geometry version, verification state, or provenance. The current accessible overview intentionally uses a list fallback instead of a data-backed map.
- `municipality_alert_coverage` is a separate reviewed, versioned, active association. Its migration rejects dynamic `alert-*` IDs and the query projects alerts only through active source/coverage-key matches. It must not be expanded by inferring geography.

### History, thresholds, trends, and forecasts

- `hydrology_telemetry` persists observed/forecast records, freshness, quality, tendency, source URL, last-successful time, and raw provider metadata. The repository overview query deliberately selects the latest row per source/station/metric/unit/horizon and does not expose a historical telemetry query.
- `hydrology_ingestion_runs` persists source-level executions; `ibera_ingest_runs` persists durable run lifecycle, source results, safe diagnostics, leases, expiry, and proof correlation. The operator run-history route is a workflow history, not an incident/case-management system.
- The current explanation compares an observed river height with the configured alert threshold, displays the provider-supplied tendency as `latest observed record`, and displays one provider forecast up to 30 days. It does not calculate a trend from a historical series, generate forecasts, or infer impact.
- The current municipality timeline is derived from the latest telemetry plus current official alerts, sorted and capped at 30 events. It is not a durable incident history with acknowledgement, assignment, escalation, resolution, or institutional case state.
- Forecast confidence is provider/contract metadata: horizons above 14 days are labeled speculative and records above 30 days are excluded. No new long-range forecast model is justified by current evidence.

### UI state and conventions

- `apps/web/src/components/government/overview.tsx` renders official source cards, evidence states, a searchable/filterable municipality list, official alerts, thresholds-derived labels, coverage gaps, and an accessible territorial fallback.
- `apps/web/src/components/government/detail.tsx` renders telemetry, evidence states, mappings, alerts, INA forecasts, provenance, the explanation panel, the current bounded timeline, and Copilot degraded/citation-unavailable states.
- `apps/web/src/components/government/ingest-panel.tsx` performs token verification, starts one ingest, renders safe results, and loads a small authenticated durable run-history list.
- The UI follows a dumb-renderer boundary: business decisions belong in the API/repository/contracts; UI should consume explicit states and semantic Tailwind tokens. Any expansion must preserve loading, empty, degraded, unavailable, and unauthorized states without inventing values.

## Source-backed slices

The following slices are feasible only when each added record remains tied to an existing or newly verified official identifier, source URL, observation time, freshness, and explicit evidence state.

1. **Institutional read workflow and durable history**
   - Extend the authenticated operator history read model beyond a minimal list to show bounded lifecycle/source outcomes and last-successful evidence already persisted in `ibera_ingest_runs`/`hydrology_ingestion_runs`.
   - Add a bounded municipality evidence-history query over persisted telemetry and current/recorded official-alert inputs, with cursor/time limits and explicit empty/degraded states.
   - Do not create acknowledgement, assignment, escalation, resolution, or human incident-case entities unless a separate institutional owner and workflow contract is approved.

2. **Verified source registry for municipality/zone expansion**
   - Add municipalities/zones only through an explicit registry of official municipality IDs, station IDs, coverage keys, source URLs, and review/version metadata.
   - Preserve the existing mapping vocabulary: association to a station or official coverage is not an influence coefficient, hydraulic relationship, or territorial impact claim.
   - Expose `supported`, `partial`, `unavailable`, or `unverified geometry` states so a new locality can be useful without fabricated coverage.

3. **Geometry status and provenance without geometry invention**
   - Add a geometry evidence envelope/status (for example: unavailable, unverified, verified-source) with source URL, dataset/version, coordinate reference system, and reviewed-at metadata only when those values are actually supplied by an authoritative source.
   - Keep the current generated square boundaries explicitly non-official and non-displayable as administrative geometry, or stop treating them as verified territory in the read model.
   - Do not add a map, polygon claim, municipality-wide coverage claim, or geometry-derived alert mapping until official geometry has been obtained and validated.

4. **Thresholds, observed trends, provider forecasts, and explanations**
   - Keep threshold comparison server-side and label it as `source mapping / threshold comparison`.
   - A trend slice may summarize a bounded sequence of observed records only with a deterministic, documented rule and evidence window; it must not imply causality or forecast generation. Prefer the provider-supplied `tendency` until a historical query proves a stable series.
   - Render provider forecasts only within the current 30-day contract and preserve `normal` versus `speculative` confidence. Do not add a new forecasting model, long-range forecast, travel-time, propagation, routing, discharge, or evacuation calculation.
   - Territorial explanation should describe which official source/station/coverage supplied the evidence and how the value compares with its configured threshold. It must not say that a mapped gauge causes, predicts, or hydraulically impacts another municipality or zone.

5. **Institutional UI expansion**
   - Add read-only history, provenance, geometry-status, trend-window, and explanation sections to the existing government routes, reusing current evidence badges and accessible list fallback.
   - Keep operator mutations limited to the existing authenticated ingest path. No client-side source selection, mapping policy, geometry editing, or incident workflow should be invented by the UI.

## Approaches

1. **Additive evidence/read-model expansion** — extend existing Zod contracts, repository queries, API view models, and government components around persisted telemetry, reviewed coverage, durable ingest runs, and verified source metadata.
   - Pros: builds on current routes and tests; preserves product separation; supports municipality expansion without fabricated geometry; keeps no-hydraulic-simulation boundary explicit; rollback is additive/read-model scoped.
   - Cons: does not provide full case management or official cartography; source registry/review remains a real operational dependency; historical queries need bounded retention and pagination decisions.
   - Effort: Medium.

2. **Full institutional incident and territorial platform** — introduce incident cases, assignments, agency workflows, official GIS layers, impact zones, and derived alert/forecast models.
   - Pros: closer to a complete institutional operating system if all authorities, datasets, and policies exist.
   - Cons: current repository has no owner, authorization, official geometry, incident lifecycle, or impact model for these claims; high risk of inventing administrative/hydraulic semantics; conflicts with the current deferred domains and would require new provider and governance decisions.
   - Effort: High.

## Recommendation

Proceed with Approach 1 as a sequence of small, source-backed read-model slices. Start with explicit evidence/provenance and bounded history contracts, then add registry-driven locality/zone coverage, then expose threshold/trend/forecast explanations in the existing overview/detail screens. Treat current square boundaries as unverified placeholders, do not publish them as official geometry, and make every unsupported locality or missing source visible as unavailable/degraded rather than filling it with inferred data. Keep the existing `EXCLUDED_TOPIC_RE` and the spec's no-routing/no-propagation/no-discharge/no-evacuation boundary unchanged.

The next proposal should define the smallest first release as: (a) durable/bounded historical evidence reads, (b) provenance/geometry-status vocabulary, and (c) one verified registry path for adding municipality/zone source associations. Trend calculations, broader geography, and institutional case management should remain separately scoped unless current source evidence makes them independently implementable.

## Risks

- **Synthetic geometry risk:** `squareBoundary()` produces squares around ports; exposing them as municipality boundaries would create an official-geography claim without evidence.
- **Mapping semantics risk:** station/coverage associations can be misread as hydraulic influence or impact. Contracts and copy must retain source mapping/threshold comparison language.
- **History retention risk:** the current overview selects latest telemetry and the existing pruning path is explicitly bounded around ledger expiry. Historical reads need a retention, pagination, and volume policy before becoming an institutional record.
- **Forecast overclaim risk:** provider forecasts up to 30 days are available, but longer horizons, generated forecasts, travel times, propagation, routing, discharge, and evacuation advice remain unsupported.
- **Source-governance risk:** adding municipalities or zones without official IDs, station relationships, URLs, and review/version metadata would create fabricated coverage.
- **Authorization risk:** ingest history is protected; future institutional workflows must not expose run diagnostics or mutate data through an unprotected browser path.
- **Contract drift risk:** the shared schema file contains both Agronautas and Iberá contracts. New types must remain explicitly Iberá-namespaced and must not transfer Agronautas queue/risk ownership.

## Ready for Proposal

Yes. The proposal should select the additive evidence/read-model approach, identify one or more independently verifiable slices, and explicitly defer official geometry publication, hydraulic/impact modeling, long-range forecasting, provider expansion without reviewed identifiers, and incident case management.
